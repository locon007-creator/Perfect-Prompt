# Perfect Prompt — Role Selection + Automatic Premium UI/UX Design

## Objective
Upgrade Perfect Prompt so app/product builds can optionally target a development role while every generated app prompt automatically receives a strong premium UI/UX and animation standard. The role changes platform conventions and implementation emphasis; the visual-quality layer is mandatory and does not require a separate user setting.

## Product Decision
Use one optional **Role** selector with an **Auto — Perfect Prompt chooses** default. Do not add a separate visual-style selector. Premium product design becomes part of Perfect Prompt’s baseline app-generation contract.

## Role Selector
Show the Role selector only when the request is classified as an app/product build. Initial choices:

- Auto — Perfect Prompt chooses
- Android App Developer
- iOS App Developer
- Web App Developer
- Full-Stack Product Engineer
- UI/UX Product Designer

Role is advisory to the compiler, not a feature request. It must never change the product purpose, workflow, requested features, or exclusions.

### Role behavior
- **Android App Developer:** favor Android/mobile conventions, thumb-friendly controls, appropriate app bars, bottom sheets/dialogs, responsive portrait layouts, and platform-appropriate interaction patterns.
- **iOS App Developer:** favor iOS-native interaction conventions, hierarchy, sheets, navigation patterns, spacing, and motion without cloning Apple assets or proprietary UI.
- **Web App Developer:** favor responsive web behavior, accessible controls, browser-safe interaction, and multi-screen/state-driven navigation where appropriate.
- **Full-Stack Product Engineer:** balance product architecture, frontend behavior, data/state correctness, and implementation constraints.
- **UI/UX Product Designer:** emphasize information architecture, interaction hierarchy, screen composition, state design, visual coherence, and polish before implementation detail.
- **Auto:** choose the closest role from the user’s explicit platform, target tool, or product context; otherwise use a platform-neutral product-engineering role.

## Automatic Premium UI/UX Standard
Every app/product prompt must include a concrete **Design & UX Standard** section generated by Prompt Master. This is mandatory even when the user never says “premium.”

The standard must require:

- production-ready visual hierarchy rather than prototype layout
- intentional spacing, typography, density, grouping, and component hierarchy
- one obvious next action on primary workflow screens
- coherent navigation appropriate to the platform and workflow
- polished empty, active, loading, completed, saved, edited, disabled, and error states only where relevant
- responsive/mobile behavior appropriate to the selected role and target
- consistent component language rather than unrelated cards/buttons
- restrained elevation, borders, surfaces, and color use
- purposeful micro-interactions and animation for navigation, state changes, sheets/dialogs, button feedback, progress changes, and completion
- respect for reduced-motion behavior when the target environment supports it
- no random decorative motion, excessive glass, neon, gradients, or animation that slows the task

### First-Screen Quality Gate
All app/product prompts must include this principle in equivalent wording:

> A functional prototype is not complete. The first main screen must look like a finished premium product. If the result resembles a generic prototype, dashboard, stack of cards, default generated UI, or placeholder composition, redesign it before presenting the build.

The gate is a quality requirement, not permission to invent new product features.

## Compiler Architecture
The existing Prompt Master runtime remains the sole compiler authority.

Data flow:

`Idea + wizard choices + optional Role → intent extraction → app/product classification → role resolution → product architecture → automatic Design & UX Standard → template render → diagnostics/repair → validation → final prompt`

### New runtime responsibilities
1. **Role normalization** — convert wizard choice or explicit role text into a stable internal role ID.
2. **Auto role resolution** — infer role only from explicit platform/target context; do not guess aggressively.
3. **Design-standard generation** — inject the mandatory app-quality contract into app/product prompts only.
4. **Platform adaptation** — role may alter interaction conventions and implementation guidance, but not core product logic.
5. **Validation** — app/product prompts fail validation if the design standard or first-screen quality gate is missing.

## UI Changes
Add one optional Role control to the app/product wizard path. Keep it visually compact and default to Auto so users can ignore it.

Do not add a separate visual-quality selector. The website should explain briefly that premium UI/UX and purposeful animation are automatic for app builds.

The role selector should not appear for unrelated writing, research, image-generation, or general prompt tasks unless a future route explicitly needs it.

## Prompt Output Structure
For app/product builds, the rendered prompt should include these concepts in a logical order:

1. Objective / Idea Lock
2. Target User
3. Main Workflow
4. Required Product Behavior
5. Role
6. Screen / information architecture as appropriate
7. Design & UX Standard
8. Constraints / Scope Lock
9. Interaction / state rules
10. Technical or tool guidance
11. Done When / quality gate

Exact heading names may vary by selected template, but the information must survive rendering and repair.

## Scope Locks
- Do not reintroduce the retired compiler.
- Do not add AI APIs, databases, authentication, analytics, billing, or new services for this feature.
- Do not create a user-facing “premium level” setting.
- Do not let role selection override explicit user requirements.
- Do not hard-code one visual style for every app; require quality and platform coherence while leaving visual expression appropriate to the product.
- Do not force animation when it harms accessibility, performance, or the primary task.

## Error / Edge Handling
- Missing role → use Auto.
- Unsupported/free-text role → map conservatively to the closest supported role or platform-neutral product engineer.
- Conflicting explicit platform and selected role → explicit user platform wins; surface a clarification only if the conflict materially affects implementation.
- Non-app task → ignore app-role UI state and do not inject the app design standard.

## Testing
Add regression coverage that proves:

- app/product builds receive the automatic Design & UX Standard
- app/product builds include the first-screen quality gate
- non-app prompts do not receive app-specific design boilerplate
- each selectable role resolves to the intended role ID and guidance
- Auto resolves from explicit Android/iOS/web context and otherwise remains platform-neutral
- role selection does not mutate product purpose/workflow/features
- the UI shows Role only for app/product flow and defaults to Auto
- existing Prompt Master parity, safety, diagnostics, templates, and compiler-authority tests remain green

Use TDD: write failing behavior tests first, then implement the minimum runtime/UI changes required.

## Completion Criteria
This upgrade is complete when a user can choose an optional build role, ignore it safely when desired, and every app/product prompt automatically carries a strong, concrete premium UI/UX and purposeful-animation contract. Generated prompts must explicitly reject prototype-quality output while preserving the user’s original product and scope. GitHub CI must pass, changes must be committed/merged to `main`, and the connected Vercel production deployment must be READY on the exact merged SHA.
